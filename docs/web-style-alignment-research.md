# 网页端显示样式与渲染：是否适合对齐？

> 调研对象：Ekko Studio **0.7.38** 的 `dist/client` 产物（CSS 令牌 + 消息渲染管线）
> 对比对象：Android 客户端 v0.12.1（Compose）
> 方法：从产物里提取真实令牌与样式值，逐项与 `Theme.kt` / `ChatMarkdown.kt` 对比；不凭印象
> 结论口径：**该对齐的对齐，不该对齐的说明理由**，不做「为了统一而统一」

---

## 一、结论先行

| 维度 | 是否适合对齐 | 理由 |
|---|---|---|
| **颜色令牌（浅色）** | ✅ 已经基本一致 | 客户端本就是按这套令牌写的，浅色值吻合 |
| **颜色令牌（深色）** | ✅ **适合，且应当修** | 客户端深色用的是**已从 0.7.38 消失的旧令牌**，与官方偏差明显 |
| **字号 / 圆角 / 代码底色** | ✅ 适合 | 官方 `--font-size-base: 14px`、`--code-bg` 等可直接照搬 |
| **消息气泡配色** | ⚠️ **不建议对齐** | 官方两条消息**用同一个底色**（`#f5f5f5` / `#292929`），只靠左右对齐区分；这与你明确要的「电报式」相反 |
| **桌面布局（玻璃拟态、520px 抽屉、hover）** | ❌ 不适合 | 移动端没有 hover，也没有 520px 侧栏的空间 |
| **行内公式（KaTeX）** | ⚠️ 适合「部分对齐」 | 官方有完整 KaTeX 字体与渲染；Android 没有等价库，只能有条件实现 |
| **Mermaid 图表** | ❌ 不适合在手机上渲染 | 官方是给文档编辑器用的；手机端更合理的是「代码块 + 浏览器打开」 |
| **代码高亮 / 表格 / 列表 / 引用** | ✅ 已对齐 | 客户端已有等价实现 |

一句话：**令牌层面该对齐（尤其深色），聊天信息架构层面不该对齐**——官方网页是「桌面仪表盘」，你要的是「电报式聊天」，两者目标不同。

## 二、令牌对比（真实十六进制，非近似）

### 浅色：已经吻合

| 令牌 | 官方 0.7.38 | 客户端 `Theme.kt` | 判定 |
|---|---|---|---|
| 正文主色 | `#1a1a1a` | `#1A1A1A` | ✅ |
| 次要文字 | `#666` | `#666666` | ✅ |
| 弱化文字 | `#999` | `#999999` | ✅ |
| 边框 | `#e0e0e0` | `#E0E0E0` | ✅ |
| 浅边框 | `#ebebeb` | `#EBEBEB` | ✅ |
| 次级背景 | `#f0f0f0` | `#F0F0F0` | ✅ |
| 卡片悬停 | `#fafafa` | `#FAFAFA` | ✅ |
| 主色 | `#333` | `#333333` | ✅ |
| 代码底色 | `#f4f4f4` | `#F4F4F4` | ✅ |
| 错误 | `#c62828` | `#C62828` | ✅ |
| 消息底 | `#f5f5f5` | `#F1F1F1`（`inkMessageBg`） | ⚠️ Δ4，可忽略 |

浅色几乎逐值吻合，说明这套令牌本来就是照官方写的。

### 深色：系统性偏差（这才是真问题）

| 令牌 | 官方 0.7.38 | 客户端现在 | 偏差 |
|---|---|---|---|
| 主文字 | `#e0e0e0` | `#EEEEEB` | 明显偏亮 |
| 次要文字 | `#a0a0a0` | `#B8BAB8` | 偏亮 |
| 弱化文字 | `#888` | `#858987` | 接近 |
| 边框 | `#3a3a3a` | `#383A39` | 接近 |
| 浅边框 | `#333` | `#2D2F2E` | 偏暗 |
| 卡片悬停 | `#333` | `#222323` | 明显偏暗 |
| 次级背景 | `#252525` | `#202121` | 偏暗 |
| 主色 | `#e0e0e0` | `#EEEEEB` | 偏亮 |
| 错误 | `#ef5350` | `#EF8C87` | **色相/明度都不同** |
| 代码底色 | `#1e1e1e` | `#131414` | 明显偏暗 |
| 消息底 | `#292929` | `#262828` | 接近 |
| 系统分隔线 | `#555` | 无此令牌 | 缺 |
| 成功 / 警告 / 信息 | `#66bb6a` / `#ffb74d` / `#6ba3d6` | **无** | 缺三个语义色 |

**根因**：客户端的深色值来自一套叫 `--ink-*` 的旧令牌体系。而 0.7.38 的产物里
`--ink-*` **一个都不存在**（实测 `grep` 计数为 0），现在的官方令牌叫
`--bg-* / --text-* / --accent-* / --msg-*`。

也就是说：**代码里那些「HStudio .xxx / --ink-*」的注释，引用的是一个已经不存在的设计系统。**
这既是视觉偏差的来源，也是注释层面的技术债（后文第五节）。

## 三、消息气泡：这是唯一「不该对齐」的关键点

官方 0.7.38 的消息配色：

```css
--msg-user-bg: #f5f5f5;        /* 浅色 */
--msg-assistant-bg: #f5f5f5;   /* 完全相同的值 */
--msg-system-border: #bdbdbd;

.dark { --msg-user-bg:#292929; --msg-assistant-bg:#292929; --msg-system-border:#555; }
```

**两条消息底色完全相同**，仅靠左右对齐 + 头像区分。这是典型的桌面仪表盘做法：
屏幕宽、信息密度低、旁边常有侧栏帮助定位。

客户端现在（v0.12.0 起）按你的要求做成了电报式：

```kotlin
telegramOutgoingBg = #DCF8C6（浅） / #2B5278（深）
telegramIncomingBg = #FFFFFF（浅） / #1E2021（深）
```

**冲突点**：如果对齐官方，就要把用户气泡的绿色/蓝色去掉，回到「两边同色」。
在手机上（88% 宽度、无侧栏）同色会显著降低扫读速度——你之前抱怨的「消息又杂又乱」，
其中一层原因就是区分度不足。

**建议**：不对齐。保留电报式配色，但**把底色取值改成官方消息底**
（`#f5f5f5` / `#292929`）作为「助手侧」，用户侧继续用强调色。这样既守住可读性，
又不引入官方调色板之外的新色。

## 四、渲染能力对比

| 能力 | 官方网页 | 客户端 | 判定 |
|---|---|---|---|
| Markdown 段落 / 标题 / 列表 / 任务项 | marked | 自研解析器（`parseChatMarkdown`） | ✅ 已有 |
| 引用块 | ✅ | ✅ `Quote` | ✅ |
| 分隔线 | ✅ | ✅ `Rule` | ✅ |
| GFM 表格 | ✅ | ✅ `Table`（含对齐、横向滚动） | ✅ |
| 代码块 + 语法高亮 | highlight.js / prism | 自研 `highlightCode`（词法着色） | ✅ 等价 |
| 行内公式 | **KaTeX**（含全套 woff2 字体） | ❌ | ⚠️ 待定 |
| 块级公式 | KaTeX | ❌ | ⚠️ 待定 |
| Mermaid 图表 | 61 个产物文件 | ❌ | ❌ 不建议手机渲染 |
| 图片内联 | ✅ | 以文件卡片 + 下载呈现 | 🟡 可增强 |
| 表格横向滚动 | ✅ | ✅（v0.6.1 起） | ✅ |

公式这一项要算成本：

- Android 没有官方 KaTeX 等价物；可选 `jlatexmath-android`（≈1.5MB）或 WebView 逐公式渲染（重、慢、耗电）。
- 你的实际使用场景（教务、论文、运维）里公式出现频率不高，但**论文仿写**场景会用到。
- 稳妥做法：**先做「公式识别 + 等宽原样显示 + 一键复制 LaTeX」**，等确实需要渲染再引入库。

## 五、顺带发现的技术债

1. **注释引用已消失的设计系统**。`MainActivity.kt` / `ChatWidgets.kt` 里大量
   `HStudio .xxx`、`--ink-*` 的说明，在 0.7.38 已无对应实现。注释不是代码，但它会
   误导后续维护（我自己就被误导过一次）。
2. **缺失语义色**：官方有 `--success/--warning/--accent-info`，客户端只有 error，
   成功/警告状态靠硬编码或复用主色。
3. **深色模式是「另一套设计」而不是「同一套的深色版」**：客户端深色背景是**纯黑 `#000000`**，
   官方是 `#1a1a1a`（深灰）。一旦对齐，深色下背景、边框、卡片、代码块的层次会更接近网页，
   也不会出现纯黑底上 `#131414` 代码块「看不出边界」的问题。

## 六、建议：分三层执行

### 第一层：直接对齐（低风险，纯取值替换）

| 项 | 动作 |
|---|---|
| 深色令牌 | `inkTextPrimary #EEEEEB → #E0E0E0`、`inkTextSecondary #B8BAB8 → #A0A0A0`、`inkBorderLight #2D2F2E → #333333`、`inkCardHover #222323 → #333333`、`inkSecondaryBg #202121 → #252525`、`inkCodeBg #131414 → #1E1E1E`、`inkAccent #EEEEEB → #E0E0E0`、`inkError #EF8C87 → #EF5350` |
| 新增语义色 | `success/warning/info` 三个令牌，值取官方 |
| 消息底 | `inkMessageBg #F1F1F1 → #F5F5F5`（浅）/ `#262828 → #292929`（深） |
| 系统分隔线 | 新增 `msgSystemBorder`：`#bdbdbd` / `#555` |
| 基准字号 | 确认正文 14sp（官方 `--font-size-base: 14px`），已基本一致 |

风险：只改颜色常量，无逻辑变化；建议同时补一个 **令牌一致性测试**（把官方值写进
测试资源，断言 `Theme.kt` 的取值与之相等），防止以后再漂移。

### 第二层：有条件对齐

| 项 | 建议 |
|---|---|
| 助手气泡底色 | 采用官方 `#f5f5f5` / `#292929`，用户气泡保留强调色 |
| 行内公式 | 先做识别 + 原样显示 + 复制 LaTeX；确有需要再评估 `jlatexmath` |
| 图片内联 | 消息里的图片直接缩略显示（点击全屏），而不是只给文件卡 |

### 第三层：明确不对齐（记录理由，避免以后反复讨论）

| 项 | 理由 |
|---|---|
| 玻璃拟态 / 侧栏 / 桌面标题栏 / hover 态 | 桌面布局，手机无对应交互模型 |
| 两边同色气泡 | 与「电报式」目标冲突，可读性下降 |
| Mermaid 渲染 | 手机屏幕与算力都不合适，改为「代码块 + 浏览器打开」 |
| 520px 抽屉宽 | 手机宽度本就是 `min(520px, 100vw)` = 100vw，等于没有 |

## 七、验收方式

1. `ThemeTokenTest`：官方令牌值固化进测试资源，断言客户端取值一致（含深色）。
2. 深色截图对比：同一会话在网页深色与 App 深色下的边框/卡片/代码块层次应一致。
3. 公式与图表：在消息里放一段 `$E=mc^2$` 和一段 ` ```mermaid `，确认 App 不崩、
   显示可读、可复制原文。
4. 不改动任何聊天交互逻辑（手势、未读、草稿、审批），只动视觉令牌。
